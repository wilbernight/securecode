# SECURITY.md — honest threat model

> **There is no such thing as unbreakable software protection.** Anyone who
> promises otherwise is selling you something. What a well-built system does
> is *raise the cost of an attack above the value of what it protects*.
> This document states exactly what each layer stops, what it does not, and
> what residual risk you carry.

---

## 1. The attack chain we killed completely

### PyInstaller extraction + bytecode decompilation — DEAD

Standard PyInstaller deployment embeds `.pyc` bytecode in the archive.
The toolchain is mature and automated:

| Tool | What it did |
|---|---|
| `pyinstxtractor` / `pyinstxtractor-ng` | unpacks the PyInstaller archive → `.pyc` files |
| `uncompyle6` / `decompyle3` | Python 3.7–3.8 `.pyc` → near-perfect source |
| `pycdc` (Decompyle++) | newer bytecode → partial source |
| dozens of GitHub-hosted decompilers | same family, improving yearly |

**Nuitka does not ship bytecode.** It translates Python to C and compiles to
native machine code (`--onefile` packs a self-extracting native payload).
There is no `.pyc`, no marshal, no zip of modules. An attacker with the EXE
has what an attacker has with any C++ binary: a disassembly problem, not a
decompilation problem. IDA/Ghidra/Binary Ninja show machine code — reading
10k lines of optimized native code to reconstruct business logic is a
project measured in expert-weeks, and the layers below make it worse.

### The brief's Layer-1 claim, stated honestly
Nuitka removes *decompilable Python bytecode*. It does not remove
*reversibility of native code*. Native code can still be read, patched and
instrumented by an expert — everything in Layers 2–5 exists to make that
maximally expensive and error-prone.

## 2. What each layer stops — and what it doesn't

### Layer 2 — Critical-code hardening (encrypted string layer)
`target_demo/protection/strings.py` is generated by
`protector/tools/build_strings_table.py`.

* **Stops:** `strings`/hex-editor greps finding error messages, registry
  value names, debugger process lists, WMI queries, master secrets. Every
  one of those is AES-256-CTR ciphertext, key derived at runtime from
  three scattered byte constants that Nuitka turns into opaque machine
  code; the key never exists as a contiguous plaintext blob in the image,
  and each entry uses its own IV.
* **Doesn't stop:** a reverse engineer who reads the decryptor in a
  disassembler can dump the table at runtime (e.g. hook the decryptor).
  Cost: hours-to-days of expert work, per release build.
* **Residual risk:** moderate — this is a cost-raiser, not a wall.

### Layer 3 — Runtime anti-debugging (`anti_debug.py`, ctypes-only)
Checks: `IsDebuggerPresent`, `CheckRemoteDebuggerPresent`,
`NtQueryInformationProcess(ProcessDebugPort/ProcessDebugObjectHandle)`,
Toolhelp32 process-name scan (x64dbg, IDA, Ghidra, Wireshark, Process
Hacker, Cheat Engine, dnSpy, Scylla, …), QPC-based timing detection
(conservative 12×-inflation threshold on multi-sample minima), optional
registry-artifact VM detection.

* **Stops:** casual analysis — the 95 % case: someone attaching x64dbg to
  see "what the license check does". The app silently exits 2–8 s later
  with exit code 0, giving no causal feedback. DEGRADE mode instead makes
  licensing fail with a generic error.
* **Doesn't stop:** kernel debuggers, hypervisor-based analysis, or anyone
  who patches the checks out of the native code. A debug-port query can be
  hidden with a driver.
* **Residual risk:** an expert bypasses it in hours; but each patched check
  must be found in optimized native code, and the watchdog keeps scanning.

### Layer 4 — Self-integrity (`integrity.py`, generated manifest)
Every launch verifies: (a) SHA-256 of the embedded Ed25519 public key vs.
its stored digest, (b) SHA-256 of the critical verification material vs.
`CRITICAL_DIGEST`, (c) the module manifest — dev mode re-hashes source
files; frozen mode requires every SDK module to import and carry Nuitka's
`__compiled__` marker.

* **Stops:** the classic offline-licensing kill shot — *swap the embedded
  public key for the attacker's own key, then self-issue serials*. Both the
  key and the digest must be found and consistently patched, and they are
  only visible as encrypted/scattered literals.
* **Doesn't stop:** an attacker who locates *and* patches both constants,
  or who NOPs the verification call itself.
* **Known gap (documented, deliberate):** a binary cannot contain a
  SHA-256 of *itself* (chicken-and-egg). Whole-image self-hashing requires
  an external step (packer or post-build digest injection) and is listed
  as future work. Current checks cover the *verification material*, which
  is the part that matters for forging licenses.

### Layer 5 — Anti-dump & memory hygiene
`SecureBuffer` (ctypes buffers, `VirtualLock` page pinning, zeroize on
close), key material re-derived per use and never cached in the client,
license-verification flow short-lived per launch.

* **Stops:** trivial `procexp`-style "save dump, grep for the key" — there
  is no long-lived plaintext key material in the client at all; artifacts
  are encrypted with machine-derived keys.
* **Doesn't stop:** full memory dumps analyzed at the right moment; Python
  strings returned by the string layer are immutable for their short life
  (honest limitation — `S()` output is the unavoidable plaintext window).

## 3. The licensing protocol — why forged serials don't work

Serial = `Base32(minified_json || Ed25519_signature)`. The client verifies
with the embedded, digest-checked public key. **The private key exists only
inside the protector**, wrapped with PBKDF2(600k)+AES-256-GCM under your
passphrase, exportable only as a passphrase-wrapped `.sec` file.

To make the protected EXE accept a fake serial, an attacker must either:
1. **Break Ed25519** — no practical attack exists (4890-bit root security,
   128-bit collision; solid against classical computers);
2. **Patch the binary** — replace the embedded public key with their own,
   defeating Layer 4's cross-checks in correct, coordinated native-code
   edits, then defeat anti-debug while doing it, then maintain that patch
   across every release; or
3. **Steal your keystore** — your passphrase is then the last line of
   defense (600k PBKDF2 iterations; a strong passphrase is not brute-forced
   from the wrapped file).

Option 3 is the realistic one — which is why the keystore lives in your
user profile, why exports demand a *separate* passphrase, and why the
README tells you to keep exports offline. **Operational security beats
crypto wizardry here.**

### Hardware lock
Fingerprint = `Base32(mask || SHA-256(salt || cpu || board || disk ||
machine_guid)[:9])`, normalized (case/whitespace), tolerance for missing
components (mask bit is part of the hash so codes never collide across
combinations). Copying a license file to another PC fails three ways:
different AES key (GCM auth), different machine code, payload mismatch.

### Offline time enforcement (clock rollback)
Three stores (GCM license file — authoritative, HKCU, decoy file), 24 h
tolerance, per-serial rollback allowance, grace then block. Uptime
cross-check catches mid-session clock changes. **Honest limit:** a user
who never launches the app while the clock is wrong, then resets it
forward before the next launch leaves no evidence — nothing can detect
that offline. Cost: the user must keep the machine unusable for the
rollback duration; for a subscription product this is usually
acceptable (renewals re-anchor time via new serials).

### Revocation & transfer
Blacklists and transfer permits are Ed25519-signed files — forged ones
fail signature verification; corrupt ones are ignored (availability).
Deactivation receipts exist because the request file itself carries the
original *signed* serial — authenticity is verifiable without trusting
the requester.

## 4. Residual risk register (summary)

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| 1 | Expert patch-out of all checks in native code | High impact, high cost | Layers 2–5 stack required coordinated edits; ship frequent releases |
| 2 | Keystore theft + weak passphrase | High | 600k PBKDF2; passphrase policy; offline exports |
| 3 | Full memory analysis at the right moment | Medium | Short-lived secrets; no long-lived keys in client |
| 4 | Clock rollback *without launching* the app | Low | Accept (offline physics); renewals re-anchor |
| 5 | One colluding customer shares their *activated* disk image | Medium | Fingerprint lock stops clones on other hardware; virtualized clones are a VM-detection policy decision |
| 6 | Demo private key in the repo | Demo only | Generate real keypairs in the protector; never reuse the demo pair |

## 5. Release checklist

1. `python protector\tools\build_strings_table.py` — rotates string-layer
   master secrets (invalidates old local licenses/clock state).
2. (Demo only) `python target_demo\tools\gen_demo_keypair.py` — fresh demo pair.
3. `python protector\tools\make_integrity_manifest.py` — Layer-4 manifest
   over the final sources.
4. `build.bat` — Nuitka onefile build.
5. `python -m tests.e2e_licensing` — 28-check protocol gate.
6. Smoke test the EXE per build.bat's printed checklist (activation →
   restart → expiry → rollback).
7. Never ship a build with `SC_DEV=1`; verify VM-detection policy
   (default OFF) matches the product's stance.
